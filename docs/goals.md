# Goals

Goal mode is opt-in. It keeps a **durable objective** active across agent turns,
rather than treating a final answer as proof that the requested work is complete.
Use a measurable end state and name all required deliverables and constraints.

## Commands

In the web or desktop composer:

```text
/goal all auth tests pass, the lint step is clean, and no tests are removed
/goal
/goal pause
/goal resume
/goal clear
```

Setting another objective replaces the current goal. `stop`, `off`, and `cancel`
are aliases for `clear`. An empty `/goal` only reads status and never starts a
model request. `/goal resume` explicitly resumes an unfinished goal, including an
active goal recovered after restart. A completed, cleared, or budget-limited goal
cannot resume; set a new goal instead. Resuming does not reset accumulated usage
or the turn limit. Wait for an in-flight turn/check to stop before resuming.

Optional limits and a required command check precede ` -- `:

```text
/goal --max-turns 10 --tokens 100000 --check 'python -m unittest' -- Finish the migration, update all callers and documentation, and preserve existing behavior
```

The command must be supplied by the user, not generated by the auditor. It runs
through the same `bash` tool as ordinary agent work, with a 120-second timeout.
Supply only trusted commands. This is not a sandbox or an adversarial grader:
repository tests may be modified by the worker. For benchmarks, keep independent
graders outside the agent's writable workspace.

Headless use:

```sh
ava -p '/goal --max-turns 10 -- Finish the migration and verify every acceptance criterion'
ava -p --session path/to/session.jsonl.zst '/goal'
ava -p --session path/to/session.jsonl.zst '/goal resume'
```

Worker output goes to stdout; goal status and reasons go to stderr. A blocked or
budget-limited run exits with code 1. Status-only commands exit 0. Goal mode does
not currently support `--record`; the normal durable session log is still written.
Put referenced file paths in the objective rather than attaching files to a
headless `/goal` command.

`/new` and `/clear` open another conversation in the UI; they are not aliases for
`/goal clear` and do not stop work in another chat.

## Runtime behavior

1. Persist a `goal/changed` snapshot in the existing append-only session log.
2. Admit a turn under the same inbox/driver ownership rules as ordinary work.
3. Record one model-visible `goal/continued` instruction per turn, before that
   turn's work. Tool results remain the latest input within the turn. If compaction
   covers the instruction, restore the goal before the retained conversation tail,
   not as a fresh user instruction after every tool result.
4. After a completed worker turn, make a separate, tool-free audit request using
   the **same configured provider, model, and effort**. The auditor sees the
   objective and textual conversation/tool evidence. Its JSON verdict says whether
   completion is proven, whether progress occurred, and why.
5. If completion is claimed and a user command check exists, run that check too.
   A failing check overrides a positive model verdict. Record command output and
   duration in `goal/checked` rather than fabricating an assistant tool call.
6. Persist the verdict. Start another turn only while the goal remains active.

The auditor does not inspect the repository independently. It can reject missing
or contradictory evidence, but it can also make mistakes. A separate model call
is not ground truth. Images and opaque reasoning are not submitted to this textual
auditor. Goals requiring visual verification need appropriate evidence and external
review; do not interpret a model verdict as a universal correctness guarantee.

The Python API follows Ava's existing explicit-driver convention:

```python
await agent.goal_command("Finish the migration and verify all acceptance criteria")
await agent.drive()
print(agent.goal)
```

Use a durable agent (`Agent.create`, `create_at`, or `reopen`). `goal_command` saves
state and returns status; the host owns scheduling `drive`.

The auditor is an additional invocation, not a second provider instance or a new
background service. Its tokens and latency are recorded as `goal-…-audit` attempts.
Audit usage does not overwrite worker context-window measurements. Session inspection
includes the final goal snapshot and counts required command checks separately as
`goal_check` tool invocations.

## Bounds and user control

- Default limit: **20 worker turns**; configurable from 1 to 1000.
- Safety limit: **50 steps per goal turn**, so a model cannot evade the turn bound
  by issuing tool calls forever.
- Optional token budget includes worker, compaction, and audit usage attributed
  to the goal. Checks have no model token cost. Missing usage stops a budgeted
  goal rather than pretending the spend was zero.
- Limits are checked at runtime boundaries, not exact provider token cutoffs. An
  already-started request may overshoot. No new substantive tool starts once the
  limit has been observed; the current implementation does not buy an extra
  model response just to summarize a budget stop.
- Three consecutive turns without verified progress block the goal. Text-only
  plans and status restatements cannot reset that counter. Semantic progress with
  tool evidence is still a model judgment, not a deterministic proof of improvement.
- Existing transport retry policy remains in force: at most two retries for
  retryable connection failures before any stream event is delivered. Goal mode
  does not add another retry layer. Final worker/audit errors block the goal.
- Pause/clear takes effect before subsequent tool or model starts. An already
  running tool/request may finish. Replacing a goal invalidates old-turn work and
  late audit results; old usage is not charged to the replacement objective.
- Existing pause/abort controls pause the active goal as well. Tool availability
  and execution policy are unchanged; goal mode grants no extra permissions.

States are `active`, `paused`, `blocked`, `budget_limited`, `complete`, and `cleared`.
Status includes the objective, turn count/limit, token usage/completeness, optional
token budget, and latest reason. The web footer displays the goal state; both UIs
show evaluation notices and support the command.

## Persistence and execution host

The session log—not the model's memory or compaction summary—is authoritative for
goal state. Snapshot writes use the existing writer and sync before acknowledgement.
Reopen restores the objective, status, limits, and recorded accounting. A repaired
interrupted goal is blocked; a budgeted one becomes budget-limited because spend
from an interrupted request may be unreported. Unknown spend is never reset to zero.

Restoring a session does not create a daemon or automatically start spending.
Explicitly resume the goal or submit work to the session. An existing live Ava
backend can keep its driver running without an attached client; restarting the
backend requires explicit goal resume. Paused, completed, and cleared goals do not
automatically reactivate.

Ava currently **awaits tools**; this feature does not introduce detached subagents,
a background-job registry, timed goal check-ins, or new job polling. A running tool
keeps its turn in flight; it is not evaluated as if it had finished. Do not launch
detached processes and expect `/goal` to supervise them. These limits differ from
Claude Code's background-task behavior.

## Research and design choices

The design was informed by [Claude Code's goal documentation](https://code.claude.com/docs/en/goal)
and [Codex's public goal implementation at commit `923c6028b69afc77e54bba78f78745ada1e46d2d`](https://github.com/openai/codex/tree/923c6028b69afc77e54bba78f78745ada1e46d2d/codex-rs/ext/goal).
These are design references, not live product-performance comparisons.

- Claude Code uses a session-scoped, prompt-based Stop-hook evaluator with a small,
  separate model. Its documentation describes completion/impossibility judgments,
  background-work handling, and bounded retry/stall behavior.
- Codex persists explicit goal states and accounting, exposes completion controls,
  and schedules continuation through the existing runtime's idle lifecycle.
- Ava reuses its own durable event log and driver, adopts a separate tool-free
  completion audit, and permits a user-supplied deterministic command veto. It
  does not copy a hook framework, add another database, or introduce a scheduler.
  Reusing the configured model is simpler operationally but can be expensive; it
  is not a claim of cost parity with Claude Code's smaller evaluator.

## Evaluation

See [the case contract](../eval/goal-cases.md) and [the initial results](goal-evaluation.md).
The live screen tied ordinary execution at 4/4, with higher token use and latency;
no general completion-rate improvement has been demonstrated. Materialize the four golden tasks:

```sh
uv run python -m eval.goal_tasks --output eval/cache/goal-tasks
uv run pytest tests/test_goal_tasks.py tests/test_goal.py
```

Use `eval/cache/goal-tasks/suite.json` with the existing benchmark runner. For an
Ava candidate arm set `"goal": true`; leave it false for ordinary execution. Freeze
separate wheels and use identical model, effort, task hashes, and timeouts. The
current ordinary baseline wheel lacks goal token limits, so comparisons using only
the shared wall-clock bound must disclose that they are not matched-token-budget
experiments. A command check is not automatically added by the benchmark adapter.

The initial four-task set is a smoke/golden screen, not a sufficient general-quality
benchmark. Lifecycle tests establish runtime behavior, not live model ability.
Goal mode should remain experimental until a paired live evaluation demonstrates
additional verified completions without false-completion or control regressions.
